# Decision handoff schemas v1

Contract between the Rust `qc-bridge` and the TypeScript agent service (ADR-0040). JSON Lines over stdio; decimal strings for money and quantity; integer nanosecond timestamps. Both sides validate against these files in tests. Change them only with a version bump (`v2/`).

**Versioning rule:** additive optional fields (new op, new optional property) are a minor version bump documented in this file — `"v"` in the envelope stays `1` and every v1 message stays valid; a breaking change (removing/renaming/tightening a field, changing an existing field's meaning) is a new directory (`v2/`), never an edit in place here.

## Protocol v1.1 (additive to v1)

Everything below is optional relative to v1: a v1-only session (`--venue sim`, the default, never calling `hello` or `report_execution`) is byte-for-byte unchanged.

- **`hello`** (new op, no extra request fields): returns `{"hello": {"protocol": "1.1", "venue_mode": "sim"|"external", "approval_public_key": "<base64 of the raw 32-byte Ed25519 public key>"}}` (`hello.schema.json`). The bridge generates a fresh Ed25519 keypair (`ed25519-dalek`, pinned exact) once per process; it is never persisted, so an old approval cannot outlive the process that minted it.
- **`--venue sim|external`** (bridge CLI flag, default `sim`): in `sim` mode an accepted `submit_order_intent` still routes to `SimVenue` exactly as in v1. In `external` mode an accepted intent is recorded in the OMS as `PendingNew` and is **never** routed to `SimVenue`; the `IntentResult` instead carries `approval` (below), and only `report_execution` (below) may move the order forward, once the gateway has talked to the real venue.
- **Approval token** (`IntentResult.approval`, `approval.schema.json`, issue #34): on acceptance in `external` mode, a short-lived, tamper-proof stamp bound to exactly the approved order, so the piece that talks to a venue (the TS gateway) can act on risk's decision without re-implementing or trusting it itself.
  - `{"payload": "<canonical JSON string>", "signature": "<base64 Ed25519 signature over the UTF-8 payload bytes>"}`.
  - Payload object, keys already alphabetical, no whitespace: `{"client_order_id":u64,"expires_ts_ns":u64,"instrument":str,"limit_price":decimal-str,"qty":decimal-str,"request_id":str,"side":"buy"|"sell","time_in_force":"ioc"|"gtc"}`.
  - **TTL: 5 seconds** of sim/market time — `expires_ts_ns` is the decision timestamp (never a wall-clock read) plus `5_000_000_000` ns.
  - A consumer (the TS gateway, or this crate's own `approval::verify`) must: verify the signature against the `hello` public key: (1) parse `payload` and check every field matches the order about to be sent, field by field; (2) check `now_ns < expires_ts_ns`. A stamp minted for one order must be rejected if presented against a changed one (different size, price or instrument); an expired stamp must be rejected even if otherwise valid. `engine/crates/bridge/src/approval.rs` is the one Rust implementation; `approval-test-vector.json` (below) is generated from it so the TS gateway can test its own verification against real Rust-signed output.
  - **Clock for step (2):** `expires_ts_ns` is `decision_ts_ns` (the bridge's own market/replay-driven clock, never a wall-clock read) plus the TTL. The gateway's `now_ns` must come from the same time domain — the real venue/market clock it is otherwise using to time its own submit — not an independent local wall-clock read, or clock skew between the two processes can silently shrink or extend the 5-second window (accepting a stale approval, or rejecting a fresh one). This is unresolved for a live gateway (issue #35, not yet built) and is flagged here rather than assumed.
- **`report_execution`** (new op, gateway -> bridge, `external` mode only; a protocol error in `sim` mode): `{"op":"report_execution","execution":{"client_order_id":u64,"event":"accepted"|"rejected"|"partially_filled"|"filled"|"canceled"|"cancel_rejected","qty"?:dec,"price"?:dec,"venue_order_id"?:str,"ts_ns":u64,"reason"?:str}}` (`order_execution.schema.json`) -> `{"ok":true}`. The bridge applies this to the OMS exactly as it would a `SimVenue` event. A legal transition applies; an illegal one (a report the OMS's own state machine cannot follow from the order's current state) is never applied and instead **halts** the engine (engages the kill switch) rather than silently ignored, since our view of position/exposure would otherwise be wrong. `venue_order_id` is a decimal-integer string today (`qc_core::VenueOrderId` is a `u64` newtype); the real broker's opaque order-id format is UNVERIFIED until #26, and this is the one place that assumption lives (`wire::parse_venue_order_id`).

## Protocol v1.2 (additive to v1.1)

Everything below is optional relative to v1.1: a v1.1-only session (no `hello.market_ts_ns`, no `kill`/`cancel_order_intent`/`reconcile` op, no `--kill-file`/`--instrument` flag) is byte-for-byte unchanged. `hello.protocol` reports `"1.2"`.

- **`market_ts_ns`** (`hello` and `status`, both required in v1.2): the latest feed/market timestamp this process has seen. The gateway **must** check an approval's expiry against this value (or a `DecisionRequest.ts_ns` it already received), never `Date.now()` — this closes the v1.1 gap where the approval TTL's clock domain was left to the gateway's own judgment.
- **`kill`** (new op) — `{"op":"kill","reason":str}` -> `{"ok":true}` (issue #44): engages the kill switch in-band, the same path as an externally-engaged one. Always succeeds (engaging an already-engaged switch is a no-op).
- **`--kill-file <path>`** (new bridge CLI flag, default none, issue #44): an out-of-band trigger independent of stdin. The bridge polls this path's existence on every record it processes and every op it dispatches, **and**, as of v1.2.1 below, on a dedicated watcher thread independent of stdin entirely; the file's existence engages the kill switch. Once engaged (by `kill`, `--kill-file`, or an external `KillSwitch` clone), the bridge cancels every open order (routed to `SimVenue` in `sim` mode; requested locally in `external` mode, where the gateway finishes the cancel for real) and refuses every new `submit_order_intent`.
- **`cancel_order_intent`** (new op) — `{"op":"cancel_order_intent","client_order_id":u64,"reason":str}`: always allowed for one of our own non-terminal orders (risk never blocks a cancel; an unknown or already-terminal id is a protocol error, `invalid_cancel`, not a silent no-op). `sim` mode routes the cancel to `SimVenue` immediately. `external` mode records `PendingCancel` and returns a signed `approval` over the canonical payload `{"action":"cancel","client_order_id":u64,"expires_ts_ns":u64}` (same key, same 5 s TTL as an order approval); `report_execution`'s `canceled`/`cancel_rejected` events then apply the real outcome, exactly as for a new order.
- **`reconcile`** (new op) — `{"op":"reconcile","venue":{"orders":[{"client_order_id":u64|null,"venue_order_id":str,"state":"open"|"filled"|"canceled"|"rejected","filled_qty":dec}],"position":dec,"cash":dec|null}}` -> `{"ok":true,"reconcile":{"ok":bool,"discrepancies":[string,...]}}` (issue #45). **Note the nesting**: the RPC envelope's top-level `"ok"` reflects only whether the request itself was well-formed — a *successfully compared* reconcile always returns `"ok":true` at that level, whether or not a discrepancy was found. The actual comparison result is `response.reconcile.ok`/`response.reconcile.discrepancies`; a caller must check that nested object, never the envelope's own `ok`, to learn whether reconciliation was clean. Compares the gateway's view of the venue with the OMS and the bridge's own position. Any discrepancy — an unknown venue order, a state or fill mismatch beyond an in-flight (`PendingNew`/`PendingCancel`) transition, or a position mismatch — **halts** (reason `"reconciliation"`); `cash` is accepted but not compared (no independent local ground truth for fees/dividends/interest). A clean compare marks the bridge reconciled. **`external` mode refuses every `submit_order_intent` until the first clean reconcile** (`risk_reject":"unreconciled"`), the same posture `qc_replay::Engine` already takes toward its own venue. `sim` mode needs no reconcile (there is no real venue) and is unaffected.
- **Instrument config** (`--instrument <path.toml>`, new bridge CLI flag, issue #66): `{id, symbol, tick_size, qty_step, min_qty, allows_fractional, trading_hours: {tz, open: "HH:MM", close: "HH:MM", days: [...]}, limits: <path>}`. When set: `DecisionRequest.instrument`/`OrderIntent.instrument` carry the real symbol instead of the v1 placeholder `"1"`; `allowed_actions` drops `"buy"`/`"sell"` outside trading hours (the engine, not the agent, decides what is offerable); a `submit_order_intent` is rejected with `risk_reject` `"outside_trading_hours"`, `"invalid_qty_step"`, or `"invalid_tick_size"` if it still tries. `limits` is a per-instrument limits file path (protected zone, same shape as `config/limits/default.toml`), used **in place of** `--limits`. `tz` supports exactly `"UTC"` and `"America/New_York"` (see `engine/crates/bridge/src/instrument.rs`'s doc comment, which also now flags that there is no market-holiday or early-close calendar); absent the flag, behaviour is byte-for-byte v1.1.
- **Structured event log** (stderr, issue #64/#44): every halt, kill-switch engagement, risk reject, reconcile result, and accepted intent writes one compact JSON line to stderr — `scripts/ops/alerts.py`'s contract, documented in that module's own docstring and `docs/runbooks/kill-switch.md`'s "Alerting" section. Stdout stays protocol-only, unchanged.
- **`decision_ledger_entry.schema.json`'s `cost_usd`** is now a decimal string, not a JSON number (this file's own money-fields-are-decimal-strings rule, above, applied where it had been missed). This field is agent-ledger-only (`out/agent/ledger.jsonl`), never sent over the bridge wire, so it isn't part of the bridge<->agent handoff proper — documented here anyway since it lives in this directory.

## Protocol v1.2.1 (additive to v1.2)

Issue #44 reopened by security review: "a hung (alive but stuck) agent loop never calls [the bridge]" (the kill-file's own docs above said as much: "provided something else keeps sending the bridge an op on a real wall-clock cadence") and "kill/halt-triggered cancels in external mode have no signed cancel approval." Both close in this version; a v1.2-only session (no `pending_cancels`/`drain_halt_cancels`, no watcher thread on the bridge side, no heartbeat on the gateway side) is byte-for-byte unchanged. `hello.protocol` still reports `"1.2"` — this round adds no new top-level `hello`/`status` required field, only the additive op/property/payload-field below, so it does not itself earn a new wire version string the way v1.1 -> v1.2 did.

- **Kill-file watcher thread** (`engine/crates/bridge/src/main.rs`'s `spawn_kill_file_watcher`, whenever `--kill-file` is given): a dedicated OS thread, independent of stdin entirely, holding its own clone of the same `Arc<AtomicBool>`-backed `KillSwitch` every engine session already shares. Polls the file every 50 ms and engages the switch itself the instant it appears — no op, no record, no cooperation from the agent process needed. The one `kill_switch_engaged` event this thread itself logs uses a wall-clock `ts_ns`, not the bridge's own sim/market clock (that clock is owned solely by the main thread this watcher must not depend on) — the one documented exception to this crate's "no wall clock" rule; see `engine/crates/bridge/CLAUDE.md` and `docs/runbooks/kill-switch.md`.
- **`pending_cancels`** (`status` and the new `drain_halt_cancels` op's response): a fresh, unexpired cancel `approval` for every order currently `PendingCancel` at the bridge — `[{"client_order_id":u64,"approval":{"payload":str,"signature":str}}]`. Minted on demand every call (never stored), so it is never stale by the time a caller acts on it even if the market clock has stopped advancing (halted, `external` mode: no more decisions, so "now" and "expires_ts_ns" are read from the same frozen clock value and the approval never appears expired). Present whether the order reached `PendingCancel` via a halt (`BridgeEngine::cancel_all_open`) or an explicit `cancel_order_intent` call.
- **`drain_halt_cancels`** (new op, no extra request fields) — `{"op":"drain_halt_cancels"}` -> `{"ok":true,"pending_cancels":[...]}` (same shape as `status`'s own field, above). Exists as a lighter-weight, op-explicit way to pull just this list; the TS gateway's heartbeat (below) actually reuses `status` since it already polls that every tick.
- **Cancel-approval payload gains an optional `reason`** (`CancelApprovalPayload`, additive field, keys stay alphabetical: `action < client_order_id < expires_ts_ns < reason`): `{"action":"cancel","client_order_id":u64,"expires_ts_ns":u64,"reason"?:"halt"}`. Present as `"halt"` only when the bridge minted the cancel itself as part of halting; omitted entirely (not merely `null`) for an explicit `cancel_order_intent` call, so that payload's wire bytes are unchanged from v1.2. Audit-only — never checked by `approval::verify_cancel`/the TS gateway's own verification, which still only checks `action`/`client_order_id`/`expires_ts_ns`.
- **The gateway's heartbeat** (`agent/src/broker/heartbeat.ts`'s `Heartbeat`, TS side, not part of the wire contract itself but the reason the two fields above exist): a real `setInterval` (default 1 s, root CLAUDE.md rule 11's budget), independent of the decision loop's own await chain, that keeps calling `status` regardless of what the loop is doing. On seeing `halted`, it reads `pending_cancels` and calls `BrokerGateway.cancelOrder` for each, retrying every tick until nothing is left open at the real broker.

## Test vector

`approval-test-vector.json` is a fixed, non-secret Ed25519 keypair (seed `[7; 32]`, test-only) plus one real payload and signature produced by `engine/crates/bridge/src/approval.rs`'s own `mint`. It exists so the TypeScript gateway can test its own signature-verification code against real Rust output without spinning up the bridge binary. Regenerated only if the canonical payload format changes; `engine/crates/bridge/tests/approval_vector.rs` checks it stays consistent with the Rust implementation on every run.
