# Study 0001: favorite-longshot bias on settled Kalshi binary markets

**Reproducibility: not reproducible from a clean clone; reproducible from the preserved snapshot.** Run 0001's raw snapshot (17 files, every sha256 matching `data/catalog/study-0001.json`) survives outside git with whoever ran it. It is not in the repository or in an approved shared store, so a fresh clone cannot rerun it. See [Reproducibility](#reproducibility).

First bounded research cycle (research-loop spec §5 A-I). The frozen plan is `REGISTRATION.md` and `config.json`, committed before any settled outcome was fetched. Results are in `RESULTS.md` and `results.json`, generated by code; the verdict and the evidence are summarized in the PR.

## Authorization assumption

Consequential assumption, made by the agent on 2026-09-27 and stated here so a maintainer can reverse it: read-only, unauthenticated `GET` requests to Kalshi's public market-data endpoints are allowed. No API keys, account endpoints, orders, demo trading or paid services were used. The hard budget was 3000 HTTP requests including retries and documentation fetches, paced at 2 requests per second, a tenth of the Basic read budget (200 tokens/s at 10 tokens per request, [rate limits](https://docs.kalshi.com/getting_started/rate_limits.md), accessed 2026-09-27). That page says every authenticated request costs tokens; how unauthenticated requests are limited is not documented (UNKNOWN).

## Files

- `kalshi_client.py`: budgeted GET client; every request, retry and failure goes to `data/raw/study-0001/requests.jsonl`, which is also the budget counter.
- `fetch.py`: listing, sampling and trade fetch into `data/raw/study-0001/` (gitignored by the existing `data/raw/` rule), then writes that snapshot's catalog (sha256 of every raw file, request counts, cutoffs, fetch times) to `out/study-0001/catalog.json` and compares it with the committed `data/catalog/study-0001.json`, which it never overwrites.
- `study.py`: selection, features, chronological split, leakage guard, metrics, decision. Offline. Refuses to run (exit 2) unless the snapshot matches every catalogued sha256.
- `tests/test_leakage.py`: the leakage guard passes clean rows and trips on a price after its decision time, a label field in a feature row, and a train label settling after the first test decision.
- `tests/test_recompute.py`: recomputes the primary metric straight from the raw JSON with separate code and asserts equality. On a clean clone only the SYNTHETIC fixture case runs, which checks plumbing only; the real-snapshot case skips.
- `tests/test_snapshot.py`: the snapshot check accepts an identical snapshot and reports a missing, edited, extra or re-logged file as a different snapshot; the committed catalog is still run 0001's.
- `record_trial.py`: appends the one registered trial to the canonical ledger `research/registry/log/trials.jsonl` via `registry.record`; refuses a second append for the same config hash.

## Commands

- `just study-0001`: rerun the analysis from the saved snapshot, then the study's tests. Without the snapshot it exits 2 and prints the missing path and every catalogued sha256. The study's tests also run in `just test`.
- `cd research && uv run python studies/0001-favorite-longshot/record_trial.py`: one-time registry append (already done for this config).

## Reproducibility

Status (2026-09-28): **not reproducible from a clean clone; reproducible from the preserved snapshot.** To make it reproducible from a clone, place the archive in an access-controlled store, after confirming Kalshi's terms allow keeping this data (UNVERIFIED). The registration stays frozen; this section describes what can and cannot be rerun.

- What exists: the committed `results.json` (sha256 `115aca0714e28b902650fe4d884f6d9b9614f5a179855fb5fe8054f8cc92e0a8`), `RESULTS.md`, and the catalog `data/catalog/study-0001.json` with the sha256 of all 17 raw files and of the request ledger `requests.jsonl` (`1898cf13...1d06b08`).
- What is missing: the raw files themselves. They were written to gitignored `data/raw/study-0001/` on the machine that ran the study (pages of dropped days were deleted during the run), and there is no approved artifact store. Whether Kalshi's terms allow redistributing these pages is UNVERIFIED, so they are not committed.
- Acquiring the snapshot: the only way to rerun run 0001 is to obtain the original files from whoever still holds them and place them in `data/raw/study-0001/`. `just study-0001` then checks every file and the ledger against the catalog before analysing anything; a single mismatch, missing file or uncatalogued file stops it with exit 2 and leaves `results.json` untouched.
- Re-fetching: `python3 fetch.py` (from this directory, spends up to the request budget) produces a new snapshot. Kalshi's listings and the request ledger change over time, so it will not match the catalog; `fetch.py` then reports DIFFERENT SNAPSHOT and exits 1. A different snapshot is a different experiment and needs its own registration and trial; it is never evidence about run 0001.
